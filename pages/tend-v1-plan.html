Tend v1: rule set and prototype plan

Two deliverables to agree before building: how the rules are structured and governed, and a clickable prototype that tests the idea with real people before the engine is real. All clinical content is a draft for dentist review.

1. Rule set structure

One rule is one small, reviewable decision. Rules are YAML files in a git repo, validated by a schema, and compiled into one versioned bundle that the app and the clinician console both read.

Repo layout

rules/
  _schema/rule.schema.json
  safety/      RF-*  (red flags)
  base/        BR-* IC-* MW-*
  restorations/ IM-* CR-* BG-* DN-*
  ortho/       OR-*
  gums/        GM-* PD-*
  risk/        FR-* DM-* CV-*
  systemic/    SY-*
  life-stage/  AG-*
  _vocab/      profile fields, steps, tools
  _tests/      golden profiles, invariants
  releases/    bundle-2026.11.0.json

Pipeline order

Profile→1 Safety gate→2 Match→3 Supersede→4 Constrain→5 Budget→6 Explain
  • Safety gate: red flags halt everything; nothing else is shown.
  • Supersede: specific rule replaces a general one.
  • Constrain: timing and incompatibility rules (e.g. fluoride rinse 30 min from brushing).
  • Budget: keep top priorities within ~8 minutes a day; trimmed items listed as "left out".

Rule schema

# every field is required unless marked optional
id: IM-001                    # category prefix + number, never reused
version: 3                    # integer, bumped on any content change
status: approved              # draft | in_review | approved | retired
when:                         # boolean over profile fields only
  all:
    - has_restoration: implant
    - not: { flag: red_flag_any }
action:
  step: interdental_brush     # key from the step vocabulary
  slot: evening               # morning | evening | both | weekly | plan | ask
  priority: high              # critical | high | normal | optional
  supersedes: [IC-001]
  requires_confirmed: false   # true = only for dentist-confirmed profiles
copy:                         # reading level checked, localized per region
  title: "Clean between teeth with an interdental brush at the implant"
  detail: "..."
  why: "..."
  ask_dentist: "Ask which brush size fits."   # optional
evidence: { grade: B, type: guideline, sources: [EFP-S3-2023] }
regions: [US, UK, EU]
safety_class: standard        # standard | elevated | high_risk (2 reviewers)
reviewed_by: [{ name: "A. Rahman, DDS", date: 2026-10-02 }]
review_expires: 2027-10-02
escalate_if: [bleeding_persists_14d, loose_implant]   # optional

Evidence grades

  • A systematic review or strong guideline consensus
  • B guideline recommendation, limited trials
  • C expert opinion or weak evidence; shown as "optional"
  • Ask never instructs; routes to the dentist

Governance

  • standard: 1 dentist reviewer
  • elevated / high_risk (implants, medication-related, systemic): 2 reviewers incl. relevant specialist
  • Review expires after 12 months; expired rules fail the build
  • Rules cannot be edited, only versioned; every release has a changelog

Hard guardrails (tests)

  • No rule may recommend a prescription product (chlorhexidine, 5000 ppm paste) except as "ask your dentist"
  • No output may contain a diagnosis phrase
  • Red flag always yields exactly one result: stop screen
  • Same profile and bundle always give identical output

Open for reviewers: medication-related issues (blood thinners, bisphosphonates), heart conditions, orthodontic sub-types and whitening are deliberately out of v1. Where a profile answer is "not sure", the engine falls back to the general rule and adds an "ask your dentist" note.

Profile fields (what the intake collects)

Required (60 seconds)

  • Age band (18-34, 35-49, 50-64, 65+)
  • Restorations: implant, crown, bridge, braces, aligners, retainer, dentures
  • Gum bleeding when cleaning (never, sometimes, often)
  • Red-flag checklist

Optional (improves the plan)

  • Gum disease history; cavities in last 3 years
  • Dry mouth, diabetes, smoking, pregnancy
  • Current tools (brush type, floss, rinse)
  • Region; next dentist visit date

Dentist-confirmable

  • Dentist adds: interdental brush sizes, fluoride strength, special instructions
  • Profile gets a "confirmed by" badge and a code
  • Unlocks requires_confirmed rules

Testing and tooling

Golden profiles

About 60 hand-written profiles with the expected output, each signed by a dentist. Any bundle change that alters a golden result needs approval.

Property tests

Generate thousands of random profiles. Assert: red flag stops all, no empty routine, no step duplicated, time budget respected, no prescription step shown as an instruction.

Clinician console

Read-only first (browse rules, trace a profile, see tests). Editing and sign-off in git review for v1, a UI in v1.5.

3. Clickable prototype plan

Goal: learn whether people complete the intake honestly, trust a four-step plan, understand the "why", and say they would keep doing it, before building the engine. The prototype is a responsive web app on the real design language with a thin real engine.

What is real

  • Intake, safety gate, routine reveal, Today, Why sheet, weekly check-in, dentist summary
  • A small client-side engine with 15 to 20 draft rules from the catalog (the live demo from phase 1, extended)
  • Local storage so a participant can return a day later

What is faked

  • No accounts, no backend, no real push reminders (simulated notification screen)
  • Guided brushing is a timer without sensors
  • Dentist confirmation is a pre-baked "confirmed" variant

What it is not

  • Not a launch candidate: content is unreviewed, so label it "research prototype"
  • Not collecting health data beyond local storage and a consented session recording

Research plan

Participants (12 total)

  • 4 with an implant, crown or bridge
  • 4 with braces or aligners (2 are parents of teens)
  • 2 with past gum disease or diabetes
  • 2 healthy adults as a contrast

Dentist review (3 to 5)

  • Walk through sample plans for 6 profiles
  • Mark each step: agree, change, unsafe
  • Ask what they would want from a patient summary

Success signals

  • ≥ 10 of 12 finish intake in under 5 min
  • ≥ 9 of 12 can say why their top step matters
  • ≥ 8 of 12 say they'd follow it for a month
  • Zero dentist ratings of "unsafe" on core rules

Timeline (about 6 weeks)

Wk 1Recruit dentist advisors and participants; finalize profile fields and step vocabulary; rule schema and validator Wk 2Dentists review the 20 prototype rules; write copy; design the remaining screens and the research script Wk 3 to 4Build the responsive prototype and engine; internal run-through with 3 golden profiles Wk 512 participant sessions (30 min), 3 to 5 dentist reviews; one-week return check with a diary Wk 6Synthesis, revised scope, go or no-go on building the v1 app and the full rule set

Suggested stack for the prototype

Static React app (Vite) with the engine as a plain TypeScript package that reads the compiled rule bundle, so the same code moves into the real app. YAML rules and schema validation with a small script; Vitest for golden and property tests; deploy to any static host. No server.
